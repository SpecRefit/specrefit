# Preview export

The editor exports the existing reviewed bytes without rerunning transformations. One file, including a selected YAML/JSON bundle, saves directly. Multiple files download as a ZIP in the browser and save directly into a chosen output folder in Electron. Configuration-file loading/saving and CLI execution remain separate work.

## User workflow and output boundary

Run **Preview these rules**, review the exact resulting files, then select **Export reviewed output**. The preview identifies the entry document. An empty rule list is supported. Changed rules, output choices and imported inputs invalidate the preview and remove the export action. Output preparation runs in the bounded worker; it does not rerun transformations. The editor is temporarily inert during output preparation and native saving, preventing replacement of the reviewed state mid-save. Cancellation and failures leave the preview available for retry.

In a browser, a single file retains its basename (with a JSON/YAML extension appended if needed); multiple files download as `specrefit-output.zip`. SpecRefit receives no source write handles or filesystem destination and does not extract archives. Download placement, renaming and overwrite prompts belong to the browser and user; SpecRefit cannot inspect their filesystem identities. Extract manually into a separate output folder. The native identity guarantees below apply to Electron's save path, not to later manual browser placement or ZIP extraction.

In Electron, one file uses a native save dialog; multiple files use a folder picker. A narrow sandboxed preload exposes only source registration and reviewed-output saving. [Electron webUtils](https://www.electronjs.org/docs/latest/api/web-utils) obtains physical paths from browser-selected Files in the isolated preload; these paths are not returned to page code. The main process verifies the invoking window, main frame and exact application URL before accepting IPC, and independently validates payload sizes, paths and collisions. The renderer cannot select an arbitrary write destination through the bridge. No general filesystem API, arbitrary IPC invocation or network permission is exposed.

## Portable archive plan

The shared engine prepares portable output paths along with the transformation preview. Output text is not changed while packaging. The retained-tree mode supports documents sharing one logical URI origin and relative JSON Pointer file references that stay inside the output tree. Absolute/root-relative references and multiple origins require the existing bundling option instead; so do single files using filename-based self-references, because renaming could break them. The preview remains inspectable and explains why export is unavailable. This avoids silently shipping broken or unexpectedly remote references. Bundling remains subject to its [documented semantic limits](bundling.md).

Paths preserve the logical document tree, including distinct directories with duplicate basenames. URI path segments are decoded exactly once. Reject traversal, encoded separators, empty segments, control characters, malformed Unicode, Windows device names/alternate streams, trailing dots/spaces, case/Unicode-normalization collisions, file/directory collisions and the unsafe `__proto__` dictionary key. Names and contents have the existing 64-file, 20 MB/file and 40 MB/total bounds. ZIP timestamps, metadata and compression are fixed. Archive bytes and contract bytes are compared across real browser and desktop workers with Node; no source timestamps, current clock or workstation paths enter the archive.

## Native source protection and replacement

All successfully imported physical documents, including missing-reference uploads, are registered before inspection. Keep both selected/resolved paths and original device/inode identities, and refresh current identities before saving. Sources remain protected throughout the app session, including after starting another project. The default example is in memory and has no physical source. The current configuration is pasted text, not a disk file; future configuration-file import must register that path through the same protection service.

The save service resolves the chosen parent, rejects source path/identity aliases and non-regular destinations, and permits replacement only of non-source output files. It writes and syncs a new exclusive temporary file in the destination directory, rechecks parent identity, source aliases and destination identity/size/timestamps, then renames the complete file into place. A failure before rename leaves that previous output intact and removes staging. Original and newly replaced source identities are both protected. Symlink outputs are rejected, including dangling links; the chosen parent is resolved and checked.

Directory export validates the complete output set and checks every destination before writing any file. Nested folders are created as needed; linked folders beneath the chosen root are rejected. The root identity and nested folders are checked again for each file. Replacement is atomic per file, not across the complete tree: a later I/O failure leaves completed files in place, reports the exact completed count and explicitly marks the export incomplete. Newly created directories can remain. Review the output folder, resolve the error and retry the unchanged preview; existing non-source outputs can be replaced. There is no automatic rollback that might overwrite intervening external edits.

As with ordinary pathname-based Node filesystem APIs, hostile concurrent directory replacement in the final check/rename interval is not eliminated. The save directory must not be concurrently controlled by an untrusted process. Detected changes abort. Crash/power-loss recovery, network-filesystem behavior and native Windows/macOS acceptance are not established by the Linux tests. No universal cross-filesystem transaction or hostile-process race immunity is claimed.

## Dependency decision — 2026-10-03

Use pinned `fflate` 0.8.3 for ZIP creation, rather than implementing a ZIP format writer. The established [upstream project](https://github.com/101arrowz/fflate) documents browser and Node compatibility. Registry metadata checked on 2026-10-03 reports MIT licensing, no runtime dependencies and recent package maintenance (metadata modified 2026-07-20). Its MIT notice is compatible with this project's Apache-2.0 distribution and is included in built notices. The pinned package has no install/postinstall script. The installed license and synchronous ZIP source were reviewed: no network, telemetry or optional fetch is involved. Use it inside the existing bounded worker; do not use library worker helpers or remote/CDN imports. The export path guard rejects the prototype-sensitive dictionary key used by the library's flattening implementation. ZIP import/extraction remains out of scope.

Set fixed ZIP timestamps, entry order, compression settings and file attributes so the same preview produces identical archive bytes. Archive paths are validated independently of logical document URIs. No archive entry may escape the archive root, collide on case-insensitive/normalizing filesystems or name a Windows device.

## Verification

`npm test` includes raw single-file output, ZIP unpacking/byte comparison, retained references, both bundle formats, timezone-independent metadata, invalid paths, collisions, absolute-reference diagnostics and native persistence tests. The latter cover nested directory writes, complete-set preflight, partial-failure reporting, safe replacement, source aliases through symlinks/hardlinks and symlinked parents, source replacement, injected pre-commit failures, concurrent destination changes, cleanup and malformed payloads.

`npm run test:browser` downloads real files and archives in Chromium, Firefox and WebKit, checks exact Node parity, transformed rather than original content, keyboard export and stale/blocked preview behavior. `npm run test:desktop` exercises the actual isolated bridge and saving service, substituting only native dialog responses to test single-file and directory cancel/save and source/hardlink rejection reproducibly. The portable-package test verifies startup without separately installed Node. All workstation execution is in WSL; native Windows/macOS packaging is the next agreed step, with unsigned development macOS artifacts because the owner has no Apple Developer account. Signing/notarization remains future work.
